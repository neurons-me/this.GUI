  const children = React.Children.toArray(props.children);

  let secondaryActionIndex = -1;
  for (let i = children.length - 1; i >= 0; i -= 1) {
    const child = children[i];
    if (isMuiElement(child, ['ListItemSecondaryAction'])) {
      secondaryActionIndex = i;
      break;
    }

  //  is ListItemSecondaryAction the last child of ListItem
  if (secondaryActionIndex !== -1 && secondaryActionIndex !== children.length - 1) {
    return new Error('MUI: You used an element after ListItemSecondaryAction. ' + 'For ListItem to detect that it has a secondary action ' + 'you must pass it as the last child to ListItem.');
  }
  return null;

# Start Here: 
Welcome to .GUI's storybook! 
Explore the components and tools that make up the .GUI ecosystem, and see how they can help you build powerful generative user interfaces with ease.
`this.GUI` is a UI framework built around three core concepts:

1. **UI spec (`this.GUI`)**: you describe the screen as data: pages, cards, text, buttons, sidebars, and children.
2. **Dynamic read/write tokens (`read` / `write`)**: instead of hardcoding everything, you can say "read this value" or "run this mutation" in a serializable way.  
   `this.GUI` also accepts the legacy aliases `$expr` / `$action`.
3. **Runtime (`runtime`, optional `.me`)**: the host decides how those reads and writes actually work, for example by resolving profile data, route params, or backend mutations.

In plain terms:

- `this.GUI` defines **what to render**
- `read` and `write` define **what should be dynamic**
- `runtime` defines **where the data comes from and what actions do**

You can run `this.GUI` in two modes:
- **JS-Only mode**: plain functions and local state.
- **Data-Driven mode**: dynamic tokens resolved by runtime (`read`, `write`).
The same spec can evolve from local UI to data-driven app without rewriting components.

const runtime = {

- static prop -> fixed UI

- `read` is resolved before render.
- `write` is hydrated into a callback.
- `$expr` / `$action` are still accepted as aliases.

## The Core Idea
The interface is a **projection of a namespace**.
This is the foundational concept. The `Namespace` exists as a source of truth, independent of any visual representation. The UI is just one of many possible ways to render it.

This leads to a clean, layered component model:

```jsx
<Namespace>        // Reality / graph / .me
  <Theme>          // Visual interpretation
    <Router>       // Focus / navigation
      <Layout>     // Spatial organization
        <UI />     // Components (atoms → organisms)
      </Layout>
    </Router>
  </Theme>
</Namespace>
```

Where each layer has a distinct responsibility:
*   **Namespace**: Defines *what exists* (the context, identity, resources, and language).
*   **Theme**: Defines *how it looks* (the visual interpretation).
*   **Router**: Defines *what is active* (the focus and navigation state).
*   **Layout**: Defines *how it is arranged* (the spatial organization).

---

## Defining "Namespace"
A namespace is the combination of:

*   **Context**: Where you are in the graph.
*   **Language**: How things are referenced (e.g., `public.ui.theme.history`).
*   **Capability**: What can be done (e.g., actions, functions).
*   **Memory**: What has happened (state, history).

This is why the `.me` object is the perfect implementation of a namespace—it's not just an identity, it's a **resolver of meaning**.

---

## The Critical Boundary
To maintain the purity of this architecture, it is essential that UI concerns **do not leak into the Namespace**.

The `Namespace` must **NOT** know about:
*   UI components
*   Layout structure
*   Styling or themes
*   Routing state

It should only concern itself with the raw semantic graph:
*   Nodes
*   Resources
*   Data
*   Actions

This separation is what enables the ultimate goal: **A runtime where the UI is just a view over a semantic graph.**

---

## The Next Step: API Definition
With this clarity, the next logical step is to formalize the `Namespace` API. This will be the primary interface for the UI to interact with the underlying graph.

A preliminary API definition could look like this:

```typescript
type Namespace = {
  get(path: string): any;
  set(path: string, value: any): void;
  call(path: string, ...args: any[]): any;
  subscribe(path: string, cb: Function): () => void;
};
```

This would be consumed within the UI via a `useNamespace()` hook, creating a clean bridge between the world of components and the world of the semantic graph.

---

## Final Insight
Following this model means we are no longer just designing components. We are designing **a language that renders itself**. The UI is simply one dialect of that language.

const runtime = buildRuntime(/* ... */);

# Router
`this.GUI` Router is the navigation kernel that maps paths to specs.

Use it when you want:
- exact pages like `/dashboard`
- dynamic routes like `/shops/:id`
- wildcard routes like `/docs/*`
- route-aware runtime context (`ctx.params`, `ctx.wildcard`)

---

## Basic Shape
```ts
import { Router } from 'this.gui';
const router = new Router({ runtime });
```

Then register routes:
```ts
router.set('/dashboard', 'me/views/dashboard/default');
```

If your route points to `me/...`, Router delegates to `runtime.resolve(...)` and the runtime returns the final GUI spec.
This is usually the best default-first setup.

---

## The Main Forms
You can use the Router in three main ways.
Recommended first to go: start with Semantic Pointer so route resolution is delegated to your runtime.

### 1. Semantic Pointer (Recommended First)
Good when the route should resolve through your runtime.
```ts
router.set('/profile', 'me/views/profile/page');
```

If the handler is a string starting with `me/`, the Router will ask `runtime.resolve(...)` for the final spec.
This is the handoff point where `this.GUI` stops being just a route matcher and starts behaving like a runtime-driven interface system.

### 2. Static Spec
Good when the route always renders the same screen.

```ts
router.set('/about', {
  type: 'Page',
  props: { title: 'About' },
  children: [
    { type: 'Typography', props: { children: 'Static route' } },
  ],
});
```

### 3. Route Factory
Good when the route depends on params, runtime context, or async data.

```ts
router.set('/shops/:id', ({ ctx }) => ({
  type: 'Page',
  props: {
    title: { read: 'me/views/shops[{{params.id}}].name' },
    subtitle: `shop id=${ctx.params.id}`,
  },
}));
```

---

## Exact, Params, And Wildcards
These are the three routing patterns you will use most often.

### Exact Route
```ts
router.set('/dashboard', () => ({
  type: 'Page',
  props: { title: 'Dashboard' },
}));
```

### Dynamic Params
```ts
router.set('/shops', 'me/views/shops/default/page');

router.set('/shops/:id', ({ ctx }) => ({
  type: 'Page',
  props: {
    title: { read: 'me/views/shops[{{params.id}}].name' },
    subtitle: { read: 'me/views/shops/default/subtitle' },
  },
}));
```

`ctx.params.id` is filled automatically from the URL.
Use `/shops` as your default route and `/shops/:id` as the dynamic specialization.

### Wildcard Route

```ts
router.set('/docs/*', ({ ctx }) => ({
  type: 'Page',
  props: {
    title: 'Docs',
    subtitle: `section=${ctx.wildcard}`,
  },
}));
```

For wildcard routes, the first `*` is exposed as `ctx.wildcard` by convention.

---

## Wiring Router To GUI
This is the standard pattern.

```ts
const router = new Router({ runtime });

router.onChange((spec, meta) => {
  GUI.mount(spec, '#root', {
    runtime,
    ctx: meta.ctx,
    showUnknown: true,
  });
});

router.navigate('/dashboard', { push: false });
```

Think of it like this:
- `Router` decides **what screen**
- `GUI.mount(...)` decides **how to render it**

---

## Resolve vs Navigate
These two methods are related, but they do different jobs.

### `resolve(path, ctx?)`
Use this when you only want the spec back.

```ts
const spec = await router.resolve('/dashboard');
```

This does **not** update browser history and does **not** notify listeners.

### `navigate(path, options?)`
Use this when you want actual navigation behavior.

```ts
await router.navigate('/dashboard', { push: true });
```

This:
- resolves the route
- updates `currentPath`
- optionally pushes browser history
- emits `onChange` to subscribers

---

## Route Context
Every route handler receives a context object:

```ts
router.set('/example/:id', ({ path, router, runtime, ctx }) => ({
  type: 'Page',
  props: {
    title: `Current path: ${path}`,
    subtitle: `id=${ctx.params.id}`,
  },
}));
```

Most of the time, the useful parts are:
- `ctx.params`
- `ctx.wildcard`
- `runtime`

# Error Handling

Error handling in `this.GUI` has three layers:

1. the boundary where routes resolve
2. the experience of async transitions
3. the content layer where runtime expressions and actions can fail

---

## Layer 1: The Boundary (Router)

The Router should absorb route failures without collapsing the whole app.

That means documenting two things clearly:

- `notFound` configuration
- async factory rejections

```ts
const router = new Router({
  runtime,
  notFound: (context, error) => ({
    type: 'Page',
    props: {
      title: 'Route failed',
      subtitle: error instanceof Error ? error.message : 'Unknown route error',
    },
  }),
});
```

Use this when:

- a route cannot resolve
- a handler throws
- an async factory rejects

The important goal is continuity: the shell stays alive even when a specific route fails.

---

## Layer 2: The Experience (Transitions)

This is where `useDeferredPending` helps.

It lets you keep loading and error policy outside the Router core:

```ts
const { showLoader, run } = useDeferredPending({ threshold: 180 });

const handleNav = async (path: string) => {
  try {
    await run(() => router.navigate(path));
  } catch (error) {
    setRouteError(error);
  }
};
```

That gives you a clean separation:

- Router resolves screens
- the hook decides when loading becomes visible
- your app decides how to render failure

## Layer 3: The Content (Runtime)

Inside the screen itself, failures can still happen in the runtime layer.

Typical sources:

- `$expr` cannot resolve
- `$action` throws
- an expression is blocked by security policy

Your goal here is graceful degradation, not silent collapse.

Patterns to favor:

- show a fallback value for failed reads
- surface action failures near the control that triggered them
